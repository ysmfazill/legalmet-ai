# Database migrations (Alembic)

Alembic is the **production** source of truth for the METRASIGHT database
schema. For zero-config local development and tests we materialise the schema
directly from the ORM models via `Base.metadata.create_all` (see
`app/db/init_db.py`), so you do not strictly need migrations to run the demo.
For any real/persistent deployment, use Alembic.

## How it is wired

- **`alembic.ini`** — config. The database URL is intentionally left blank here.
- **`alembic/env.py`** — injects `sqlalchemy.url` from application settings
  (the `DATABASE_URL` environment variable / `.env`), and points
  `target_metadata` at `Base.metadata`. Importing `app.models` registers every
  table, so `--autogenerate` sees the full schema. `render_as_batch` is enabled
  automatically on SQLite so ALTER-style migrations work there too.

No credentials are ever stored in `alembic.ini` — they come from the same
environment configuration the app uses.

## Common commands

Run from `services/api/` with the virtualenv active and `DATABASE_URL` set
(defaults to the SQLite dev database):

```bash
# Autogenerate a migration from ORM model changes
alembic revision --autogenerate -m "describe your change"

# Apply migrations up to the latest revision
alembic upgrade head

# Roll back the most recent revision
alembic downgrade -1

# Show current revision / full history
alembic current
alembic history --verbose
```

## Notes

- Review every autogenerated migration before committing — autogenerate does
  not detect everything (e.g. some server-default or type changes), and batch
  mode on SQLite has known limitations.
- The naming convention on `Base.metadata` (see `app/db/base.py`) keeps
  constraint names deterministic across PostgreSQL and SQLite, which keeps
  autogenerated diffs stable.
